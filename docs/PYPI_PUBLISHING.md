# PyPI publishing

MobiOrigin uses PyPI Trusted Publishing through GitHub Actions. The publishing
job receives a short-lived OpenID Connect credential. The repository must not
store a PyPI password or API token.

## Resolved release-size gate

The MobiOrigin 0.1.2 wheel is 112,586,809 bytes and its source distribution is
112,614,838 bytes. PyPI accepts at most 100,000,000 bytes per file by default.
That historical model-inclusive release could not be uploaded to PyPI.

The publishing workflow enforces this limit before requesting an upload
credential. It cannot partially publish an oversized release.

The frozen model checkpoints account for approximately 121 MB before archive
compression. A PyPI-compatible release must keep the exact checkpoint bytes and
hashes while moving their transport outside the Python wheel. The supported
route is a versioned GitHub release asset retrieved atomically by MobiOrigin,
with the archive identity and all five model-artifact identities verified before
the model directory is published locally. A package that silently omits models
or changes their numerical representation is not acceptable.

MobiOrigin 0.1.3 implements this design and is public at
<https://pypi.org/project/mobiorigin/0.1.3/>. The published wheel is 127,499
bytes and the source distribution is 156,316 bytes. The model bundle remains a
separate 121,098,240-byte GitHub release asset whose SHA-256 is verified before
extraction.

## Trusted Publisher configuration

The first upload used a pending GitHub publisher with these exact values. PyPI
converted it to the active project publisher after successful publication:

- PyPI project name: `mobiorigin`
- GitHub owner: `Raza-pl`
- GitHub repository: `MobiOrigin`
- Workflow filename: `publish-pypi.yml`
- GitHub environment: `pypi`

Create a GitHub environment named `pypi`. Repositories with multiple maintainers
can add a deployment-approval rule there. The workflow grants `id-token: write`
only to the publishing job. The build job has read-only repository access and
runs separately.

## Release contract

The workflow accepts only an existing `vMAJOR.MINOR.PATCH` tag whose version is
identical to `pyproject.toml`. It builds from that tag, validates both
distributions with Twine, rejects files over the PyPI limit, and transfers the
verified build artifact to the isolated publishing job. PyPI attestations are
generated by the official PyPA publishing action.

For every release, verify the external project page and install the public wheel
in a fresh environment before updating installation claims.
